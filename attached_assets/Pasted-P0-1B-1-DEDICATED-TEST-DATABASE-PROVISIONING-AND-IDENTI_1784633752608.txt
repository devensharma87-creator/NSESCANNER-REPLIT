P0.1B-1 — DEDICATED TEST DATABASE PROVISIONING AND IDENTITY ATTESTATION

OWNER AUTHORIZATION

The owner authorizes creation of one dedicated, disposable PostgreSQL test database/cluster and one restricted test-runner role.

This authorization applies only to a new test resource.

It does not authorize modification, cloning, migration, restoration, deletion or repurposing of:

- the current development database;
- the production database;
- any legacy Neon database;
- any paper-trading database;
- any database containing trading, ledger, signal, audit or user data.

OBJECTIVE

Provision and attest a third database environment used only for automated tests.

This stage must:

1. Identify the current database topology without exposing credentials.
2. Create a new empty test-only resource if the platform supports it safely.
3. Ensure it is not the development or production database.
4. Create a restricted non-production test role.
5. Create an immutable test-environment identity marker.
6. store test credentials only in the development/test execution context;
7. prove that production deployment cannot receive the test credentials;
8. leave all DB/application tests hard-blocked.
9. Run no application tests, migrations or trading code.

This is provisioning and identity attestation only. Test execution is deferred to P0.1B-2.

BRANCH AND CODE RULES

Work only on:

phase0/authorized-remediation-20260720

Do not:

- merge to main;
- push;
- publish or deploy;
- restart workflows;
- run application code;
- run Vitest;
- run typecheck unless source files are changed;
- modify trading, signal, scheduler, provider, UI or production runtime code;
- disable the current `DB_TEST_RUNTIME_NOT_AUTHORIZED` hard block;
- add a normal environment-variable bypass for the hard block.

PERMITTED EXTERNAL STATE CHANGE

You may create only:

- one new empty test-only PostgreSQL resource;
- one owner/provisioning role if required by the provider;
- one restricted test-runner role;
- test-control schema/identity objects inside the new test database;
- development/test-only secrets needed to access that new resource.

Do not copy development or production data.

Do not publish the application while creating the resource.

STAGE 1 — BASELINE

Before any external change, report:

- current branch;
- current HEAD;
- main SHA;
- Git status;
- current P0.1A acceptance status;
- whether any automatic checkpoint occurred;
- confirmation that `DB_TEST_RUNTIME_NOT_AUTHORIZED` remains active.

Stop if the branch is wrong, main moved unexpectedly or tracked production files contain unexplained changes.

STAGE 2 — DATABASE TOPOLOGY INVENTORY

Use read-only Replit database metadata/settings and static environment-name inspection.

Do not print any connection string, password, token, certificate or secret.

Identify separately:

1. Editor/development database.
2. Published production database.
3. Any retained legacy Neon database.
4. Any deployment-preview database.
5. Whether Replit permits a third independent database in this project.
6. Whether a separate Replit test app/remix is required.
7. Whether an external isolated PostgreSQL project is required.

For every identified database, report only:

- provider: Replit Helium, Neon or other;
- purpose;
- environment;
- PostgreSQL version if available;
- database name redacted to a safe label;
- host fingerprint/hash, not raw credentials;
- whether Agent can mutate it;
- whether production uses it;
- whether it contains existing data;
- whether it is eligible for destructive automated tests.

Never print the raw hostname if Replit treats it as sensitive. A SHA-256 fingerprint of normalized host/port/database identity is sufficient for the report.

Required eligibility result:

- DEVELOPMENT: NOT_ELIGIBLE
- PRODUCTION: NOT_ELIGIBLE
- LEGACY/SHARED: NOT_ELIGIBLE
- DEPLOYMENT_PREVIEW: eligible only if it is independently disposable and cannot affect production
- NEW DEDICATED TEST RESOURCE: ELIGIBLE

Do not infer that a different database name on the same production server is adequate isolation.

STAGE 3 — PROVISIONING DECISION

Preferred order:

1. A new independent test database/cluster supported by Replit.
2. A separate non-published Replit test app with its own development database, provided the test runner can safely operate there.
3. A new dedicated external PostgreSQL test project/branch with no relationship to the operational database.

Do not use:

- the current development database;
- the production database;
- a new schema inside either operational database;
- a new database on the same production cluster unless independent cluster isolation is proven;
- a clone containing production or development rows;
- a legacy shared Neon endpoint;
- a local mock database presented as PostgreSQL-equivalent.

If Replit Coder cannot create a genuinely independent resource through authorized tools, stop before provisioning and return exact owner UI instructions. Do not improvise.

STAGE 4 — NEW RESOURCE REQUIREMENTS

If automated provisioning is safely available, create one resource named with a clearly test-only convention, for example:

nsescanner-automated-test-20260721

Requirements:

- PostgreSQL 16 where supported;
- empty database;
- no copied schemas or rows;
- no production backup/restore;
- no development backup/restore;
- closest practical region to the application;
- lowest-cost test-appropriate configuration;

- clearly tagged TEST_ONLY/DISPOSABLE;
- no public exposure unless required for the test runner;
- TLS required for any remote connection;
- certificate verification enabled where supported.

Do not delete the resource at the end of this stage.

STAGE 5 — ROLE AND PRIVILEGE MODEL

Inside the new test resource only, create:

1. Provisioning/owner role, if provider-managed ownership is insufficient.
2. Restricted runner role, preferably:

   nsescanner_test_runner

Runner role must be:

- NOSUPERUSER;
- NOCREATEDB;
- NOCREATEROLE;
- NOREPLICATION;
- NOBYPASSRLS;
- unable to access any other database;
- unable to assume another role;
- unable to read provider/system secrets;
- unable to modify the identity marker;
- allowed to connect only to the test database;
- allowed to create/drop run-specific schemas inside that test database only;
- allowed to run migrations and tests only inside run-specific test schemas.

Apply safe session defaults where supported:

- finite statement timeout;
- finite lock timeout;
- finite idle-in-transaction timeout;
- explicit application name;
- no unrestricted search path.

Revoke unnecessary `PUBLIC` privileges.

Report the resulting privilege booleans without printing passwords.

STAGE 6 — IMMUTABLE TEST IDENTITY

Inside the new test database only, create a protected control schema such as:

test_control

Create an identity table containing exactly one environment record with:

- randomly generated immutable UUID;
- environment class `AUTOMATED_TEST_ONLY`;
- creation timestamp;
- provider/resource identifier or safe fingerprint;
- expected database name;
- expected restricted role;
- schema version;
- owner-approved purpose.

Requirements:

- the restricted runner receives SELECT only on this identity object;
- the restricted runner cannot INSERT, UPDATE, DELETE, TRUNCATE, ALTER or DROP it;
- the marker is owned by the provisioning/provider owner;
- no production/development identity or data is copied.

Call the identity value:

TEST_DB_IDENTITY_UUID

Do not print its full value publicly. In reports, show only a safe short fingerprint.

STAGE 8 — READ-ONLY IDENTITY ATTESTATION

After provisioning, a direct PostgreSQL connection to the new test resource is authorized solely for identity/privilege verification.

Do not import application modules.

Do not run migrations.

Do not create application tables.

Do not run tests.

Using the restricted runner connection:

1. Prove the connection targets the expected test database.
2. Prove current role equals the expected runner role.
3. Prove server/host fingerprint matches expected test identity.
4. Prove port matches.
5. Prove TLS state and policy.
6. Read the protected identity marker.
7. Prove identity UUID/fingerprint matches the expected value.
8. Prove environment class is `AUTOMATED_TEST_ONLY`.
9. Prove the role flags:
   - not superuser;
   - not create-role;
   - not create-database;
   - not replication;
   - not bypass-RLS.
10. Prove the runner cannot connect to operational databases.
11. Prove the database contains no application tables or copied business rows.
12. Prove only the intended test-control objects exist.
13. Prove the runner cannot modify the identity table.

For the final negative privilege check, use a transaction that is rolled back and target only a harmless test-control operation in the new test database. Do not touch any operational database.

If safe negative verification cannot be designed without mutation risk, report it as unverified rather than improvising.
