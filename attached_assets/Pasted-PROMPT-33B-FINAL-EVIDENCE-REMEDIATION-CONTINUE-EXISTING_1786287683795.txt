## Gate 3 — Complete F&O-ban admission semantics

```ts
type FnoBanAdmissionResult = {
  status: "CURRENT" | "LAST_KNOWN_STALE" | "UNAVAILABLE";
  banned: boolean | null;
  canAuthorizeAdmission: boolean;
  asOf: string | null;
  reasonCode:
    | "FNO_BAN_CURRENT_CLEAR"
    | "FNO_BAN_CURRENT_BANNED"
    | "FNO_BAN_LAST_KNOWN_STALE"
    | "FNO_BAN_UNAVAILABLE"
    | "FNO_BAN_MALFORMED";
};
```

Admission rules:

* `CURRENT + canAuthorizeAdmission=true + banned=false` → this gate may pass.
* `CURRENT + banned=true` → block.
* `LAST_KNOWN_STALE` → block, whether the cached list contains the symbol or not.
* `UNAVAILABLE` → block.
* Malformed/unknown result → block.
* `null` must never be interpreted as `false`.
* A stale list must never authorize a new derivatives position.

Remove any “future stale gate” language. Stale blocking must be implemented now.

Inventory every real production function capable of:

* emitting an F&O signal
* admitting an F&O candidate
* staging an F&O trade

## Gate 5 — Make PostgreSQL persistence truly durable

Changing:

```ts
void _saveSnapshotToDb(...)
```

to:

```ts
await _saveSnapshotToDb(...)
```

is insufficient if `_saveSnapshotToDb()` catches and suppresses the database error.

Required behaviour:

1. PostgreSQL is the authoritative durable store.
2. Local disk is only an optional, non-authoritative L1 cache.
3. The caller must receive an explicit persistence result.
4. A failed database write must never be reported as durable success.
5. A database write failure must:

   * preserve the previous validated snapshot
   * emit structured diagnostics
   * increment a failure metric
   * produce a stable reason code
   * never replace the last-good snapshot
6. A newly fetched snapshot becomes durable only after its PostgreSQL transaction commits.
7. Do not silently swallow persistence errors.

Use an explicit result or controlled exception:

```ts
type SnapshotPersistenceResult =
  | {
      ok: true;
      snapshotId: string;
      committedAt: string;
      sha256: string;
    }
  | {
      ok: false;
      reasonCode: string;
      errorClass: string;
    };
```

Persist:

* Snapshot ID
* Source URL
* Effective date
* Retrieval timestamp
* SHA-256
* Schema version
* Validation status
* Row count
* Normalized records
* Parse-reject count
* Duplicate counts
* Created/committed timestamp

Schema creation/migration must be additive, idempotent and non-destructive.
