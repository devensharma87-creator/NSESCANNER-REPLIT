## 1. Executive verdict

The project is not a fake scanner or a cosmetic prototype. It has a serious architecture: Kite-first data policy, provenance types, F&O signal tiers, paper-trade gates, signal-plan immutability, durable gross/charges/net fields, Swing staging, Telegram controls, audit logs, and a large automated test estate.

However, it is **not yet safe to call production-grade automated trading infrastructure**. The production deployment itself reports `FAIL/DEGRADED`, blocks auto-opens because of database latency, and shows a P0 paper-ledger drift of **+₹8,00,644.80**. It is currently best classified as:

- **Professional analytics / supervised paper-trading platform:** strong but operationally fragile.
- **Unattended paper-trading engine:** not yet fully proven end to end.
- **Real-money auto-trading engine:** not ready; broker execution should remain disabled.

The most serious issues are not indicator selection. They are accounting truth, conflicting canonical data states, gross-versus-net risk decisions, failure semantics, schema/deployment drift, public-read exposure, incomplete exchange-calendar logic, non-reproducible builds, and gaps between unit-tested components and a proven live scheduler-to-exit lifecycle.

**Immediate decision:** keep all real broker execution disabled. Do not treat the current F&O paper ledger, P&L headline, scanner BUY labels, pre/post scenario levels, strategy recommendations, or drawdown percentage as trade-decision grade until the P0/P1 items below are closed.

## 4. Critical and high-priority source findings

### P0-01 — Trading-risk gates disarm when their data/query fails

**Evidence:** `artifacts/api-server/src/lib/optionSignalGates.ts`

The following failure paths explicitly fail open:

- stopped-today query failure returns `0`, disarming the circuit breaker;
- paper-stop query failure returns `0`, disarming the executed-trade breaker;
- recent-stop query failure disables bias-flip cooldown;
- setup win-rate query failure disables the low-win-rate gate;
- NIFTY return failure disables relative-strength conflict;
- VIX failure returns `spike:false`, disabling the volatility-shock gate.

This creates the wrong dependency direction: the platform becomes **less restrictive when observability/data is degraded**. That may be acceptable for informational cards, but not for tradeable emission or auto-open.

**Required fix:** introduce gate criticality classes. Execution-critical risk gates must return `UNKNOWN/BLOCKED`, not `PASS`, when their evidence is unavailable. Advisory scoring factors may fail neutral only with a visible `DEGRADED` reason. Persist every unknown-gate decision in `fno_signal_reasoning`.

### P0-02 — F&O option-leg liquidity probe fails open

**Evidence:** `artifacts/api-server/src/lib/paperTradingFO.ts` around the option-chain liquidity probe.

If the fresh option-chain fetch throws or returns null, the paper trade proceeds using only the premium/LTP gate. That means spread and OI protection can disappear precisely when option-chain infrastructure is degraded.

**Required fix:** for automatic opens, chain-unavailable must be `DATA_BLOCKED_OPTION_CHAIN`, unless a separately approved emergency mode has a stricter premium, spread-history and quantity cap. Manual paper trades may remain possible with a prominent override record.

### P0-03 — Public mode is a global, persistent owner-equivalent GET bypass

**Evidence:** `artifacts/api-server/src/lib/publicAccess.ts`, `lib/userAuth.ts`, `routes/userAuth.ts`.

When public mode is on, `/auth/me` returns an authenticated synthetic owner with every tab. `requireOwner` bypasses GET/HEAD authentication. The flag:

- has no automatic expiry;
- survives restarts via a disk cache;
- exposes broad owner-read surfaces, including paper reports and diagnostics;
- can diverge across autoscaled instances because it is file-backed, not centrally stored.

Writes are correctly blocked for anonymous visitors, but read exposure is still excessive and the “temporary” label is misleading without a TTL.

**Required fix:** remove synthetic-owner public mode. Replace it with a DB-backed, signed, read-only `AUDITOR` role/token; allowlist specific routes; redact user/trade/account/security fields; default TTL 30–60 minutes; enforce one central expiry; provide immediate revocation and audit logs.

### P0-04 — Source schema changes are not accompanied by a complete executable migration path

**Evidence:** `lib/db/src/schema/optionSignals.ts`, `columnWidthInvariants.test.ts`, `optionSignalPlanSchema.ts`.

The repository documents a 17 July live incident where a 42-character writer version hit a `varchar(32)` column and dropped inserts for about 54 minutes. The Drizzle declaration is now widened to 64, but the located runtime ensure only adds the premium-lock column/table; it does not widen `writer_version`, `execution_status`, or sibling reasoning columns.

Therefore a clean code deploy does not prove an existing database has the new widths. The invariant test only checks hard-coded TypeScript numbers; it does not inspect the real DB schema.

**Required fix:** add an idempotent, owner-approved migration script with preflight/postflight queries against `information_schema.columns`; fail deployment before market open if widths are wrong. Add a production migration ledger. Never depend on manual DDL plus updated TypeScript declarations.

### P0-05 — No end-to-end proof of the full F&O and Swing lifecycle

The project’s own verification index admits that live Kite, Telegram and the full scheduler paper-trade cycle are not E2E tested. Unit tests prove functions, not the production chain:

`Kite tick/candle → signal → trigger → contract validation → paper open → MTM → exit → charges → ledger → report → Telegram`.

The same gap exists for Swing:

`daily scan → candidate → staging → approval → paper open → monitoring → exit → reconciliation → alert/report`.

**Required fix:** create deterministic replay fixtures plus a production-safe shadow canary that exercises each transition without broker orders. Acceptance must reconcile signal ID, fingerprint, paper-trade ID, premiums, charges, account balance and Telegram delivery-log ID.

## 5. Build, contract and test defects

### P1-01 — Canonical full TypeScript build is currently red

`columnWidthInvariants.test.ts` includes `"EMITTED"` in `CanonicalDecision[]`, while `CanonicalDecision` no longer permits that value. The direct full build fails with TS2322.

This shows taxonomy/test drift and means “full typecheck green” is false at the audited commit. Runtime Vitest still passes this file because transpilation does not enforce the TypeScript error.

### P1-02 — Frozen dependency installation is not reproducible

`pnpm install --frozen-lockfile` fails because root override configuration does not match `pnpm-lock.yaml`. Reproducible CI/deployment cannot rely on the committed lockfile until it is regenerated and reviewed.

### P1-03 — Critical unit tests are not hermetic

Five selected critical suites could not even collect without `DATABASE_URL`, including anti-flip, Swing staging, premium-path and provenance/honesty suites. They import the live DB module before mocks isolate it.

Observed results:

- API selection: **235 tests passed**, but **7 suites failed to collect** solely due to missing `DATABASE_URL` across two runs.
- Scanner selection: **83/83 tests passed**.
- Application package typechecks were clean when run separately; the full solution failed on the taxonomy test noted above.

**Required fix:** split pure logic from DB adapters; mock the DB before module evaluation; keep separate `unit`, `integration-db`, `replay`, and `live-smoke` commands. CI must not count “0 tests” suites as coverage.

### P1-04 — Two different constants share the name `CURRENT_WRITER_VERSION`

- Paper trade rows: `paper-writer-v1.2.0-ledger-net`.
- F&O reasoning/history instrumentation: `paper-writer-v1.3.0-reasoning-instrumented`.

They may intentionally version different writers, but identical exported names invite wrong imports and mistaken reconciliation filters.

**Required fix:** rename to `PAPER_TRADE_WRITER_VERSION` and `FNO_REASONING_WRITER_VERSION`; document their table ownership and compatibility matrix.

## 6. Market-calendar, time and scheduler issues

### P1-05 — Trading-day logic is Monday–Friday only

`fnoTradingDays.ts` explicitly does not exclude NSE/BSE holidays. Consequences:

- false signal-gap alerts on holidays;
- incorrect “trading sessions since” counts;
- misleading scheduler/report-health metrics;
- possible holiday execution attempts if other checks also use weekday-only rules.

**Required fix:** central exchange-calendar service with NSE and BSE calendars, special sessions, Muhurat trading, unscheduled closures and versioned source metadata. Every scheduler, market-status calculation, signal-gap counter and report date must use it.

### P1-06 — Time handling is duplicated through manual `+5.5h` arithmetic

Many files create IST dates by adding 5.5 hours and slicing ISO strings. India has no DST, but repeated hand-built conversions still create boundary and semantics risk (instant versus exchange date versus naive IST candle time).

**Required fix:** one `exchangeClock` module defining `istDateKey`, session windows, exchange day and serialization rules; ban new manual offsets with an import-guard test.

### P1-07 — Runtime DDL is mixed with application boot

The app schedules additive schema changes 15–16 seconds after process boot. Writers can start before a migration succeeds, and autoscaled instances can run concurrent DDL. A failed boot job is logged but may leave code/schema mismatched.

**Required fix:** run pre-deploy migrations before traffic; make application readiness fail closed on required-schema mismatch. Runtime `ADD COLUMN IF NOT EXISTS` should be an emergency compatibility layer, not the primary migration system.

## 7. F&O trading-methodology findings

### P1-08 — Risk protection is split between emission gates and execution gates with inconsistent failure policy

Some execution gates correctly fail closed (tradeability, baseline stats, premium validity, auto-trading flag), while other gates fail open (chain liquidity and several session-wide risk queries). This makes the system hard to reason about and can produce a card labelled tradeable even when a required risk input is unknown.

**Fix:** define a single machine-readable gate contract: `PASS | FAIL | UNKNOWN`, `criticality`, `source`, `asOf`, `freshnessMs`, `reason`, and `appliesTo = DISPLAY/EMISSION/AUTO_OPEN`. Auto-open requires every critical gate to be PASS.

### P1-09 — Signal taxonomy remains in transition

The source still intentionally writes legacy `reason_code='DEMOTED'` or `'EMITTED'` while canonical fields carry different semantics, and contains an open `TODO-P0.4-writer-fix`. This dual vocabulary can cause inaccurate counts, popup wording or dashboards if a consumer reads the legacy field.

**Fix:** inventory every consumer; migrate it to canonical fields; add consumer-contract tests; then stop writing legacy decision values. Do not remove legacy columns until historical reports are version-aware.

### P1-10 — Historical/backtest P&L mixes pricing modes by design

The Backtest Lab honestly supports both real captured premiums and a directional delta proxy. Labels are present, which is good, but aggregate statistics can still be misread if REAL_REPLAY and proxy-priced runs are compared or rolled up together.

**Fix:** never aggregate across pricing modes by default; make pricing mode a mandatory filter and export column; exclude proxy trades from “realized-like” headline P&L; report snapshot coverage and survivorship/missing-data exclusions beside every result.

### P1-11 — Option execution realism remains approximate

The cost model assumes one ₹20 order each side and fixed spread/slippage bps. It does not model partial fills, order modification, rejection, freeze quantity, market protection, depth, latency or expiry-exercise settlement. This is acceptable only as a clearly labelled estimate.

**Fix:** store bid/ask at decision and fill time, quote age, depth/quantity, modeled fill rule and rejection reason. Maintain gross, statutory charges, spread and slippage separately. Validate statutory rates from a versioned broker/exchange schedule before each effective date.

## 8. Swing trading findings

### P1-12 — Approval and paper-open are separate commits

Swing approval is committed before `openPaperEquityTradeFromStagedOrder`. If the paper open fails, the order remains approved and only a nested `paperTradeResult` explains the failure. This is honest but operationally ambiguous and can look like “approved = trade taken.”

**Fix:** use explicit states such as `APPROVED_PENDING_PAPER_OPEN`, `PAPER_OPENED`, `APPROVED_BUT_BLOCKED`, and `PAPER_OPEN_ERROR`; persist the paper-trade ID or block reason on the staging row. Dashboards and Telegram must distinguish approval from execution.

### P1-13 — Capital-diagnostic failure leaves the approved response incomplete

After a failed paper open, the capital lookup intentionally fails open so approval response still succeeds. This does not create a trade, but it can hide the real reason from the owner.

**Fix:** persist `PAPER_OPEN_ERROR/UNKNOWN_DIAGNOSTIC` and alert the owner. Do not silently return an approved row with an empty reason.

### P1-14 — Swing fallback data must remain structurally prevented from staging

The Swing scanner still has Kite-first/Yahoo-fallback data paths. The UI and trust layer label Yahoo as INFO_ONLY, which is a strength. The remaining risk is regression through a future consumer that stages directly from scan rows.

**Fix:** enforce on the server that staging cannot accept client-asserted trust. Require a fresh server-side Kite quote and daily-bar provenance, which the current staging contract already aims to do; add an import/contract test proving every staging entry point calls the same trust gate.

## 9. Reporting, accounting and data issues

### P1-15 — Durable charges are improved, but production reconciliation still needs DB proof

The schema and writers now contain `gross_pnl`, `charges_total`, itemized breakdown, model version, `net_pnl` and status. This is a major strength. But without the live DB, this audit cannot verify:

- columns exist with correct types in every environment;
- every post-fix closed trade has `charges_status=CURRENT`;
- account balance equals seed + capital events + correctly versioned gross/net realized P&L;
- no close path bypasses charge stamping;
- legacy rows are never silently reconstructed as historical truth.

**Required production query pack:** null ratios by writer version, balance identity, duplicate close detection, gross-net arithmetic, component sum, charge-model version distribution, and segment-wise reconciliation.

### P1-16 — Data freshness and provider status need production evidence, not only UI badges

The provenance architecture is strong, but operational readiness must prove actual live coverage: Kite session age, WebSocket last tick, candle last bar, option-chain age, universe coverage, failed symbols, source distribution and cache age.

**Fix:** one canonical `/data-health/market` contract plus immutable per-run snapshots. Signal and paper-trade rows should reference the exact data-health snapshot ID used at decision time.

## 10. What is strong and should be preserved

- Kite is explicitly authoritative for price-sensitive/trading paths.
- Yahoo is mostly constrained to labelled analytics/display use.
- F&O signal tiers and demotion semantics exist.
- Recovery/chase/anti-flip concepts, plan immutability and audit history exist.
- Paper auto-open flag is designed to fail closed.
- Premium validity and contract identity gates are present.
- Gross/charges/net separation and model versioning are materially better than the older audit baseline.
- Swing staged-entry wording correctly distinguishes staged limit price from Kite risk-evaluation LTP.
- Real broker Swing execution remains hard-disabled.
- Scanner and portfolio math have substantial pure test coverage.
- Backtest proxy data is labelled instead of being presented as captured market truth.

Do not weaken these while fixing the defects.
