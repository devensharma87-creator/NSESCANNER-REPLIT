BACKGROUND

The current tick replay path retains approximately 400,000 entries in an array.

The prior audit found that once the array reaches capacity, trimming uses operations such as:

- Array.shift()
- Array.splice(0, n)

These operations move the remaining array contents and can become O(n) per incoming tick.

At the current small subscription set this may remain hidden. At the future approved universe of approximately 7,890 subscriptions, it could create:

- High CPU consumption
- Event-loop lag
- Garbage-collection pressure
- Slow quote processing
- Stale displayed data
- WebSocket disconnects
- Delayed SSE delivery
- Incorrect freshness classifications

The replay buffer is diagnostic/replay infrastructure. It is not the future historical candle warehouse and must never be used to fabricate technical indicators.

OBJECTIVE

Replace the current shifting/splicing replay structure with a strictly bounded O(1) circular/ring buffer while preserving externally required replay semantics.

Do not change provider subscriptions, tick content, freshness thresholds, canonical identity or business behaviour.

C. IMPLEMENT A TRUE O(1) BOUNDED RING BUFFER

Implement a fixed-capacity circular buffer with:

- Preallocated or bounded storage
- Head/write index
- Current size
- Configured capacity
- O(1) append
- O(1) overwrite of the oldest entry when full
- No `shift()`
- No front-removal `splice()`
- No array reallocation proportional to retained history on every append
- Deterministic oldest-to-newest snapshot output
- Correct wrap-around behaviour
- Explicit empty/full state
- Capacity validation

Required invariants:

- `0 <= size <= capacity`
- Append never increases retained size above capacity.
- At capacity, one append evicts exactly the oldest entry.
- Ordering remains oldest to newest when read.
- No tick is duplicated or silently reordered.
- NSE and BSE instruments with the same symbol remain separate through `canonicalInstrumentId`.
- Index aliases do not create duplicate replay entries unless two actual provider events occurred.
- Identity-less ticks remain fail-closed according to the accepted Phase 0.5A contract.
- Buffer reset returns it to a valid empty state.
- Consumer mutation cannot corrupt internal storage.

Do not use an external package unless strictly necessary. Prefer a small internal implementation.

E. READ-PATH PERFORMANCE

Appending must be O(1).

Snapshot creation may be O(n) because returning all retained entries necessarily requires reading them, but:

- It must happen only when a consumer requests a snapshot.
- It must not happen on every tick.
- Filtering should avoid repeated full copies where a bounded iterator can safely be used.
- No unbounded JSON serialization may execute inside the WebSocket tick handler.
- No replay read should mutate the ring.

If any existing consumer requests the entire 400,000-entry buffer frequently, report it as:
