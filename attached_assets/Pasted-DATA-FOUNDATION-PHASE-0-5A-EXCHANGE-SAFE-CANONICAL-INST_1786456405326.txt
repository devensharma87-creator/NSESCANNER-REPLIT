DATA FOUNDATION PHASE 0.5A — EXCHANGE-SAFE CANONICAL INSTRUMENT IDENTITY

CODER_EXECUTION_CONTRACT remains active.

This is one bounded development task. Work only on eliminating NSE/BSE quote collisions and establishing the canonical instrument identity required by the future data foundation.

Do not implement WebSocket expansion, three-shard subscriptions, Reserved VM changes, historical candles, indicators, fundamentals, charting tools or whole-site migration in this task.

Do not deploy.

BACKGROUND

The verified intended live universe is:

- NSE mapped live securities: 2,971
- BSE mapped live securities: 4,710
- All NSE/BSE indices: 209
- Required Kite tokens: 7,890
- Kite capacity: 9,000
- Headroom: 1,110

A P0 defect was identified:

The current live quote store appears to use symbol alone as its key:

liveQuotes.set(symbol, tick)

For securities listed on both NSE and BSE, one exchange can overwrite the other. This violates the requirement that every exchange-listed security have a distinct canonical identity and can create cross-tab price discrepancies.

OBJECTIVE

Implement one exchange-qualified canonical instrument identity throughout the live-feed storage and retrieval path, while preserving current functionality and without increasing subscription count.

A. REPRODUCTION BEFORE MODIFICATION

Before changing code, produce a deterministic failing test showing:

1. An NSE instrument and BSE instrument with the same trading symbol.
2. Different instrument tokens and different prices.
3. Both ticks entering the current quote-storage path.
4. One overwriting the other or becoming indistinguishable under the current symbol-only key.
5. The exact affected functions and consumers.

Label this evidence TESTED.

Do not use production provider calls or mutate production data.

B. CANONICAL IDENTITY CONTRACT

Define one centralized identity type/helper. Do not let individual modules invent their own key format.

Minimum canonical identity fields:

- canonicalInstrumentId
- exchange
- segment
- tradingSymbol
- providerInstrumentToken
- providerExchangeToken
- securityId
- ISIN where available
- securityClass
- listingStatus

Canonical key requirements:

- NSE and BSE instruments with the same symbol must remain different.
- Instrument token must resolve to exactly one canonical identity.
- Exchange-qualified identity must be preserved through API and UI contracts.
- Never use symbol alone as an identity key.
- Never use symbol-only matching to join official masters with provider masters.
- Do not silently deduplicate cross-listed companies by ISIN; NSE and BSE listings remain separate market instruments.
- The design must support future Kite and Upstox token mappings without changing the canonical identity.
- The design must support future canonical candles, EMA, RSI, SMC, FVG, BOS, volume profile and Fibonacci calculations without using provider-specific identity as the analytical primary key.

Prefer an explicit canonical key such as an immutable internal ID derived from exchange-qualified authoritative identity. Explain the selected format and collision properties.

C. LIVE QUOTE STORE

Update the live quote path so that:

- Quotes are stored by canonical instrument identity or provider instrument token mapped to canonical identity.
- NSE and BSE versions of the same symbol cannot overwrite each other.
- Index identities cannot collide with stock identities.
- Existing symbol-search convenience may remain only as a secondary lookup returning one or more exact exchange-qualified matches.
- Ambiguous symbol-only lookup must return an explicit ambiguity result, not silently choose an exchange.
- Every quote retains exchange, token, timestamp, provider and canonicalInstrumentId.
- Existing current subscriptions remain unchanged.

Do not label data LIVE merely because it exists in the map. Preserve the current freshness behaviour; do not alter thresholds.
