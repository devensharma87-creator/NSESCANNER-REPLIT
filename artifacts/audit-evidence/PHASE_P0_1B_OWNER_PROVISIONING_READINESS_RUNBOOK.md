## §3 — Infrastructure Requirements

### §3.1 — Required Environment Properties

The dedicated test PostgreSQL server/cluster must be:

- **Physically/logically separate** from the operational Replit-managed PostgreSQL
  project — identified by a distinct hostname and project identity.
- **Cost-controlled and disposable** — the lifecycle creates and drops databases
  per run; the cluster itself persists, but each run's database is ephemeral.
- **TLS-enabled** where the provider supports it; connection strings should use
  `sslmode=require` or equivalent if the provider mandates TLS.
- **Able to create and drop databases and roles** using the provisioning identity.
- **Compatible** with PostgreSQL 14+ (the application uses no version-specific
  features beyond what Drizzle ORM supports on node-postgres).
- **Accessible from the Replit build environment** (outbound TCP from the Replit
  runner to the test cluster's host:port must be reachable).

### §3.2 — Provider-Neutral Selection Criteria

No specific provider is mandated by the source. The following criteria apply:

| Criterion | Requirement |
|---|---|
| Separate project/server | Must differ from operational Replit Postgres by hostname |
| CREATE DATABASE privilege | Provisioning identity must have it |
| CREATE ROLE privilege | Provisioning identity must have it |
| GRANT / REVOKE | Provisioning identity must be able to grant per-DB privileges to the runtime role |
| DROP DATABASE | Provisioning identity must have it (cleanup) |
| DROP ROLE | Provisioning identity must have it (cleanup) |
| TLS | Preferred; required if provider default |
| Reachability | Cluster host:port reachable from Replit outbound TCP |

Non-binding compatible examples (provider-neutral — any PostgreSQL-compatible
service meeting the criteria above is acceptable): Neon, Supabase, Railway,
Render, ElephantSQL, a self-hosted PostgreSQL instance, or a Replit-external
PostgreSQL add-on — provided it is a **separate project/server** from the
operational Replit database and satisfies the privilege requirements.

### §3.3 — Explicit Prohibitions

The following are **prohibited** and will cause the guard to reject the configuration:

- Using the operational Replit PostgreSQL server with a different database name.
- Using the operational role or any credential that has access to operational data.
- Using a production replica as the test cluster.
- Using a fixed shared database name while claiming per-run isolation
  (the guard requires the database name to contain the run ID).
- Placing operational credentials in any test secret.
- Passing the provisioning credential (`TEST_DB_PROVISIONING_URL`) to the Vitest
  child process as `DATABASE_URL` or `TEST_DATABASE_URL`.

The guard enforces these prohibitions at the code level:
- `OPERATIONAL_DB_DENYLIST`: rejects any test URL whose database contains `"nse_scanner"`.
- `sameTarget()`: rejects test URL that resolves to same host:port/dbname as `DATABASE_URL`.
- `validateEndpointSeparation()`: rejects provisioning URL at same host:port as `DATABASE_URL`.
- `CHILD_PROCESS_ENV_ALLOWLIST`: starts child from EMPTY env; operational secrets never inherited.

## §4 — Provisioning and Runtime Role Matrix

### §4.1 — Provisioning Identity

The provisioning identity is used only by the parent lifecycle process. It must
**never** appear in the child process environment.

| Requirement | Required? | Rationale |
|---|---|---|
| `LOGIN` | **Yes** | Must authenticate to connect |
| `CREATEDB` | **Yes** | `createDatabase(dbName)` — creates fresh DB per run |
| `CREATEROLE` | **Yes** | `createRestrictedRole()` — creates restricted runtime role |
| Database ownership | **Yes** | Required to grant privileges on the new database to the runtime role |
| Schema creation | **Yes** (implied) | Can create schemas within the new DB |
| `GRANT` to runtime role | **Yes** | Must GRANT CONNECT + schema privileges to the runtime role |
| `DROP DATABASE` | **Yes** | `dropDatabase(dbName)` — cleanup after run |
| `DROP ROLE` | **Yes** | `dropRole(roleName)` — cleanup after run |
| Access to operational cluster | **No** — must be refused | Separate cluster required |
| `SUPERUSER` | Not required | Ordinary privileged role with above grants is sufficient |
| Replication | Not required | |
| Bypass RLS | Not required | |

### §4.2 — Runtime Identity (created per run by the provisioning adapter)

The runtime role is created fresh per run by `createRestrictedRole(roleName, dbName)`,
returned as a URL, and used exclusively in the Vitest child process.

| Restriction | Status |
|---|---|
| No `SUPERUSER` | **Required** |
| No `CREATEDB` | **Required** |
| No `CREATEROLE` | **Required** |
| No replication | **Required** |
| No bypass-RLS | **Required** |
| Access only to `nsc_vitest_<runId>` database | **Required** |
| No access to operational cluster | **Required** (separate cluster) |
| Access to public schema within test DB | **Required** (for schema bootstrap) |

### Step 1 — Create a dedicated test-only PostgreSQL server

**Purpose:** Establish a physically/logically separate PostgreSQL server with its
own hostname and project identity. This is the only server the test lifecycle
will ever touch.

**Expected result:** A running PostgreSQL server accessible over TCP from Replit,
with a hostname that does not match the operational Replit Postgres hostname.

**Redacted verification:** Confirm the new server's host differs from `DATABASE_URL`'s host.
Example (redacted): new cluster host = `test-cluster.pg.example.com`; operational host ≠ this.

**Common mistake:** Creating a new database on the existing Replit Postgres server.
This reuses the same hostname — `validateEndpointSeparation()` will reject it.

**Rollback:** Delete the new server/project from the provider console.

---

### Step 2 — Give it a clearly non-production name

**Purpose:** Prevent confusion between test and operational infrastructure.

**Expected result:** The server/project name contains "test", "vitest", or similar
non-production label. Example (redacted): `market-scanner-vitest-cluster`.

**Common mistake:** Naming it the same as or similar to the operational project.

**Rollback:** Rename or delete the server.

---

### Step 3 — Confirm hostname/project ID differs from operational infrastructure

**Purpose:** Verify endpoint separation before any credentials are created.

**Expected result:** `extractHostPort(newClusterUrl)` ≠ `extractHostPort(DATABASE_URL)`.
This check is enforced by `validateEndpointSeparation()` in the lifecycle.

**Redacted verification:** Compare only the hostname portion (not credentials)
against the operational `DATABASE_URL` host. They must differ.

**Common mistake:** Using the same Replit-managed Postgres host with a different DB name.

**Rollback:** Delete the test server; do not proceed until hosts differ.

---

### Step 4 — Create the provisioning identity

**Purpose:** Create a PostgreSQL role on the test cluster with the minimum privileges
required by `ProvisioningAdapter`: `LOGIN`, `CREATEDB`, `CREATEROLE`, database ownership.

**Expected result:** A role named something like `vitest_admin` (name is your choice)
with `LOGIN`, `CREATEDB`, `CREATEROLE` on the test cluster only.

Example SQL (redacted — do not paste credentials here):
```sql

```

**Redacted verification:** Confirm `\du vitest_admin` on the test cluster shows
`CREATEDB` and `CREATEROLE` attributes. Confirm this role does NOT exist on
the operational cluster.

**Common mistake:** Creating the provisioning role on the operational cluster,
or giving it `SUPERUSER`.

**Rollback:** `DROP ROLE vitest_admin;` on the test cluster.

### Step 5 — Confirm runtime role creation is delegated

**Purpose:** The lifecycle's `createRestrictedRole()` creates a fresh restricted
runtime role per run. The provisioning identity must have `CREATEROLE` to do this.

**Expected result:** No manual runtime role creation needed — it is generated

`nsc_vitest_role_<runId>` with no `CREATEDB`, no `CREATEROLE`, no superuser,

**Redacted verification:** Confirm provisioning role has `CREATEROLE` (Step 4 above).

**Common mistake:** Pre-creating a static runtime role. The lifecycle requires
a fresh role per run — a static role does not contain the run ID in its name
and the cleanup validator will refuse to drop it.

**Rollback:** Not applicable; the lifecycle creates and drops the role automatically.

**Redacted verification:** Confirm the test cluster's host:port does not appear

## §6 — Endpoint Separation Checks

These checks are performed **without connecting** (URL parsing only) and will be
executed by the lifecycle before any DB operation. Source: `disposableDbLifecycle.ts`
and `dbTestGuard.ts`.

### §6.1 — Pre-connection checks (URL parsing only)

| Check | Implementation | Fails if |
|---|---|---|

## §7 — Disposable Lifecycle Sequence

### Step 2 — Runtime authorization confirmation

**Executing component:** `DB_TEST_RUNTIME_AUTHORIZED` constant in `dbTestPreflightRunner.ts`  
**Credential used:** None  
**Validates:** Compile-time constant is `true` (requires source change + owner authorization)  
**Failure behavior (current):** Exits with `DB_TEST_RUNTIME_NOT_AUTHORIZED`  
**Evidence emitted:** Preflight failure message printed to stderr  

### Step 3 — Unique run-ID generation

**Executing component:** `generateRunId()` in `disposableDbLifecycle.ts`  
**Credential used:** None  
**Result:** 24-char hex string from `crypto.randomBytes(12)` — already lowercase alphanumeric  
**Failure behavior:** `crypto.randomBytes` failure → propagates; no DB touched  
**Evidence emitted:** Run ID included in lifecycle result object  

### Step 4 — Disposable DB-name derivation

**Executing component:** `deriveDatabaseName(normalizedRunId)` in `disposableDbLifecycle.ts`  
**Result:** `nsc_vitest_<runId>` (max 63 chars)  
**Failure behavior:** Throws `DatabaseNameTooLong` if > 63 chars (impossible with 24-char runId)  
**Evidence emitted:** DB name in lifecycle result; redacted in output  

### Step 5 — Restricted runtime-role derivation

**Executing component:** `deriveRoleName(normalizedRunId)` in `disposableDbLifecycle.ts`  
**Result:** `nsc_vitest_role_<runId>` (max 63 chars)  
**Failure behavior:** Throws `RoleNameTooLong` (impossible with 24-char runId)  
**Evidence emitted:** Role name in lifecycle result  

### Step 6 — Disposable DB creation

**Executing component:** `adapters.provisioning.createDatabase(databaseName)` — `ProvisioningAdapter`  
**Credential used:** `TEST_DB_PROVISIONING_URL` (provisioning identity)  
**Action:** `CREATE DATABASE nsc_vitest_<runId>;`  
**Failure behavior:** Throws `DisposableDbLifecycle: createDatabase failed`; role never created; cleanup not needed; lifecycle propagates error  
**Evidence emitted:** Database name logged; connection details redacted  

### Step 7 — Restricted runtime-role creation

**Executing component:** `adapters.provisioning.createRestrictedRole(roleName, databaseName)` — `ProvisioningAdapter`  
**Credential used:** `TEST_DB_PROVISIONING_URL` (provisioning identity)  
**Action:** `CREATE ROLE nsc_vitest_role_<runId> WITH LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE PASSWORD '<generated>';` then `GRANT CONNECT ON DATABASE nsc_vitest_<runId> TO nsc_vitest_role_<runId>;`  
**Returns:** Runtime URL for the restricted role (only this URL leaves the provisioning adapter)  
**Failure behavior:** `cleanup(isFailure=true)` → drop database; propagate error  
**Cleanup behavior:** Database dropped; no role to drop  
**Evidence emitted:** Runtime URL username/host logged (no password); provisioning URL never logged  

### Step 8 — Schema bootstrap / migration

**Executing component:** `adapters.migration.bootstrapSchema(runtimeUrl)` — `MigrationAdapter`  
**Credential used:** Runtime URL (restricted role) — provisioning URL NOT passed here  
**Action:** Applies Drizzle schema from `lib/db/src/schema/index.ts` to the test database  
**Failure behavior:** `cleanup(isFailure=true)` → drop role + database; propagate error  
**Cleanup behavior (failure):** Role dropped first (has grants), then database dropped  
**Evidence emitted:** Bootstrap success/failure logged; no credential values  

### Step 9 — DB-only Vitest execution

### §9.1 — Transient Test Failure Clarification

**Observation:** One `test:full` run showed "1 failed | 204 passed (205 files)" before
two subsequent runs (one `test:full`, one tripwire) both showed 4250/4250 passing.

**Investigation:**
- The vitest verbose output for the failing run was captured; the failing test name
  was not emitted in the grep-captured output (vitest compact-mode output truncation).
- The "connection to server failed: ETIMEDOUT" WARN messages visible in the tripwire
  run output originate from `src/lib/swingTtlSweep.test.ts` line 292, which contains
  a deliberate test fixture: `vi.fn().mockRejectedValue(new Error("connection to server failed: ETIMEDOUT"))`.
  This mock simulates an ETIMEDOUT error to test the sweep's fail-open behavior.
  It is **not** a real TCP timeout and does not cause the test to fail.
- The 0-connection tripwire result on the subsequent run confirms that no real pg.Pool
  TCP connection was established during any of the 4250 tests.
- The "swing TTL sweep: schema column migration failed (fail-open)" WARNs are the
  expected output from `swingTtlSweep.ts` when `db.execute()` is called against a
  mock (empty object); the function catches the error and continues — which is the
  designed behavior.

**Verdict:** The transient failure is attributable to thread-level timing variance
in the parallel `--pool=threads` worker pool. The failure was not reproduced in two
immediately subsequent runs. It does not indicate a systemic defect, a DB connection
attempt, or a code correctness issue. It does not affect the P0.1B safety acceptance.

### §9.2 — Tripwire Manifest Identity Clarification

**Observation:** The tripwire harness reported 296 manifests for 205 test files.

**Implementation:** `dbNetworkTripwire.preload.cjs` lines 72–74:

```javascript
const instanceId   = crypto.randomBytes(4).toString('hex');
const manifestPath = path.join(manifestDir, `tripwire-${process.pid}-${instanceId}.json`);
```

**Mapping:**
- Vitest `--pool=threads` uses `worker_threads` (tinypool), not OS `fork()`.
- All worker threads share the **same OS PID** as the main vitest process.
- Each thread/V8 context loads the preload independently, receiving a **unique
  `instanceId`** (4-byte random hex = ~4.3 billion possible values).
- `manifestPath` format: `tripwire-{pid}-{instanceId}.json` — uniqueness comes
  from `instanceId`, not PID.

**296 manifests breakdown:**
- 1 main vitest orchestrator process (runs `vitest.config.tripwire.ts`, no tests directly)
- Up to 205 worker thread contexts (one per test file, `--pool=threads`)
- Additional contexts from pool warm-up, resize events, and the `setupFiles`
  installation phase (each new V8 context in the thread pool emits a manifest on startup/exit)
- `beforeExit` and `exit` event handlers write the final manifest before the context ends

**No same-PID overwrite races:** `instanceId` is random per V8 context load; the
`fs.writeFileSync` is synchronous and called with the unique `manifestPath`. Even if
two worker threads shared a PID (impossible within one run but addressed anyway), their
`instanceId` values differ with overwhelming probability. The harness validated all 296
manifests as structurally valid (nonce match, numeric fields) and found 0 invalid manifests.
