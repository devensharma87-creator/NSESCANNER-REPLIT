---
name: Lazy schema migration deadlocks inside rolled-back test transactions
description: A memoized "ensure schema columns" helper called for the first time inside an open tx-rollback test self-deadlocks; must pre-warm it in beforeAll using the raw db, not inside the tx.
---

Any lazy/memoized `ensureXSchemaColumns()` helper that runs `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` on its first call will request an ACCESS EXCLUSIVE lock on that table. If a DB-integration test wraps everything in one long-lived, never-committed `db.transaction(async (tx) => { ...; tx.rollback(); })` and that transaction already holds row locks on the same table (e.g. from an `INSERT` via `tx`), then triggering the memoized migration for the first time from *inside* that transaction (even via a different code path/connection) blocks forever waiting for the lock — the open tx never releases it because it can't proceed past the still-hanging migration call. Symptom: the test times out at vitest's default 5000ms with zero diagnostic output when piped through `tail`/redirection (the crash looks like the whole vitest process died silently); redirecting to a plain log file with `--reporter=verbose` and reading it separately reveals the real per-test `Test timed out in 5000ms` message.

**Why:** `ADD COLUMN IF NOT EXISTS` still needs to acquire the ACCESS EXCLUSIVE lock to check the no-op condition — idempotency only skips the *change*, not the lock acquisition. A memoized guard (`migrationPromise` pattern) makes this a true footgun: calling the *raw* `applyXSchemaColumns()` in a test's `beforeAll` is NOT enough, because it bypasses the memo cache — the first *internal* call to the memoized `ensureXSchemaColumns()` (e.g. from a write helper invoked later inside the tx) still sees the cache empty and re-issues the ALTER, deadlocking again.

**How to apply:** In any DB-integration test that wraps its scenario in one rolled-back transaction, call the *memoized* `ensureXSchemaColumns()` (not the raw `applyXSchemaColumns()`) once in a `beforeAll`, using the plain (non-tx) `db` handle, before any transaction-wrapped test runs. This warms the module-level cache so every later call — including ones triggered from inside the open tx — just awaits the already-resolved promise instead of re-touching the DB. Reference pattern: `swingTtlSweep.test.ts`'s `beforeAll` (though that module has no internal memoized re-trigger from its business-logic path, so it only needed the one-time raw call — modules whose write path DOES call the memoized ensure-fn on every write need the memoized variant pre-warmed, not the raw one).
